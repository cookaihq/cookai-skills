# 调查、必要性与改造

先读取实际目标及项目规则；报告文件或函数证据，尚未确认的事实不转成选项让用户猜。对已有配置只调查定义、加载、存储与字段存在性，预览用合成值。

## 调查结果

| 对象 | 必须查清的事实 | 需要用户决定的内容 |
| --- | --- | --- |
| 配置 | 持久字段、默认/显式/继承、敏感项、只读项、依赖；每个作用域的全部文件与真实顺序、全局启用条件、缺项/空值/读取错误语义、逐字段来源与整组绑定；允许保存的目标、位置与共享影响、验证和重载方式、配置命令、缺项/修复路径及调用方 | 是否需要可视化配置管理；分组、显示与编辑方式；尚未确定的保存范围 |
| 产物 | 文件/结构化结果/远端资源/操作回执；项目与任务归属；可取得的当前与历史记录；缺失、失败、部分完成、过期状态 | 是否需要成果展示；内容、操作、刷新与保留方案 |
| 业务与既有界面 | 用户完成任务的顺序、配置与结果的关系、现有页面、运行环境、组件、用户操作与接入成本 | 保留、补充、替换，或先看新界面后决定；统一界面还是多个页面；模板是否适合 |
| 分发 | Skill/Plugin、共享核心、现有定制、宿主入口、已登记验收 Agent | 沿用已确认范围；缺少实际验收名单时询问 |

依次作出三个独立判断，每项给出业务证据、推荐及取舍，沿用用户已确认的选择：

1. **功能必要性**：需要哪些可视化能力，是否需要新增 UI。无持久设置、无可用成果或已有界面足够的目标可以省略相应能力；不为展示而强加日志、数据表或历史采集。
2. **页面组织**：围绕实际操作流程选择统一界面、单个专注页面或多个页面。配置与结果同时存在也可以在一套工作台内完成；功能分类不决定页面或服务数量。
3. **实现选型**：比较保留/改造已有界面、采用或局部复用本 Skill 的模板、完全定制。以交互适合程度、已有技术和维护成本决定；完全定制可以不引入共用运行代码。

配置方案及既有入口的处置遵守 [配置方式与存量改造](configuration.md#配置方式与存量改造)。已退出的配置方式列为必要调整，不再作为保留选项；用户对其他界面的选择仍按上表确认。多层配置的展示方案需区分生效来源与保存目标，预览至少说明仅覆盖一项、移除后的具体回退，以及低优先级文件保存后仍被覆盖的过程。

## 复杂需求澄清

在初次需求、追加调整和预览反馈中持续判断。先查源码、已有记录及已确认决定；只有**多个相互影响的改动**与**仍会改变方案的关键缺口**同时存在，才主动推荐 `mattpocock-skills:grill-with-docs`。关键缺口包括对象关系、任务边界、记录来源或历史覆盖等尚未明确，且不同答案会改变数据、交互或改造范围。简单调整直接处理，单个必要问题普通澄清；复杂但已说明充分的需求继续原流程。

推荐时指出本次具体的关联与缺口，说明现在梳理能确定什么，再询问用户是否使用该 Skill。比如同时调整产物目录、任务命名和任务／会话／文件三种视图，但任务与会话的关系、旧记录覆盖仍未明确；应说明这些答案如何影响目录与视图设计，而非仅说“需求复杂”。在同一提示中提供当前宿主真实可用的显式调用入口。

先核对当前宿主的已安装插件、用户命令或技能选择器；仅显式调用的入口可能不在模型可自动调用的清单中，不能据此断言未安装。Codex 核实入口后可提示用户发送 `$mattpocock-skills:grill-with-docs`，Claude Code 使用已核实的 `/mattpocock-skills:grill-with-docs`；WorkBuddy 按当前客户端实际提供的入口引导，不照搬其他宿主语法。无法核实入口或未安装时，如实说明，可继续普通澄清；用户要求安装时再处理安装，不把它变成 UI 工作的前置依赖。

按用户选择衔接：

- 用户选择使用：保留当前目标、阶段、已确认决定和待梳理缺口。`grill-with-docs` 是仅用户显式调用的入口；用户只回复“同意”“采用建议”，尚未显式点名时，给出可直接发送的调用提示并等待。只有用户实际点名或使用宿主的显式入口后，才读取并执行该流程；不以读取缓存文件或调用其下游 Skill 代替用户触发。
- 用户已显式点名或已进入该流程：沿用本次选择，不再问是否使用；只梳理尚未解决或已发生变化的部分。
- 用户拒绝：继续普通澄清，在当前任务中记住该决定，同一缺口不反复推荐。出现实质不同的新问题才重新判断；推荐未获回应也不视为同意，能独立推进的调查继续进行。

梳理结束后，将结论接回原设计、预览或实施阶段；保留已有有效决定，说明本轮新增结论和仍会影响方案的问题。关键缺口已解决或用户已明确接受取舍，才推进受其影响的部分；不重新开始整套流程，也不把选择澄清当成实施授权。文档按目标项目的落位规则更新已有记录，不在本 Skill 内复制第三方访谈或文档工作流。

## 最小展示确认

先说明实际页面名称、各页面承担的能力、主要操作流程和选用的实现。只为涉及的能力提供对应内容：配置表写清字段、用途、分组、控件、敏感/只读、默认/继承、联动、保存目标、生效时机与共享影响；产物视图表写清内容、记录依据、呈现方式、允许操作、历史覆盖、缺失/过期处理。统一界面可在同一方案中说明，不要求两套表单或两张页面；无需 UI 时不提交展示表或预览。一次问完互相关联的关键选择，已确认内容保留，不重复询问。

有记录缺口时，让用户选择现有数据范围或补充记录。补充前提供具体方案：采集哪些数据、何时采集、存在哪里、保留多久、能否补历史、对原运行及隐私的影响。确认前只用明确标记的合成数据预览，不制造历史成果。

## 改造顺序

1. 调查 → 功能必要性、页面组织、模板选择及已有 UI 处置确认；无需 UI 则交付结论。
2. 具体展示/记录方案 → 新增或明显变化界面可运行预览 → 用户评审。
3. 按选型改造既有界面、接入所选模板或实现定制界面，落实任务关联和适用的生命周期 → 原功能及实际 UI 验收。
4. 核对真实发布包、安装使用说明、页面重开入口与数据保留 → 交付。

再次改造先读取既有决策、业务定制和实际采用的依赖清单。用户可以只请求评估、只做预览或调整其中一个页面；按该阶段推进。预览使用独立数据目录，不能写真实配置。配置和产物的通用语义按实际涉及能力适用，模板布局与适配协议仅约束采用对应实现的部分。
