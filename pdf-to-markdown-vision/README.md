# PDF 视觉转 Markdown

将技术 PDF 转成忠实的 Markdown 和真实图片，保留图文关系、表格条件、公式以及可复查的处理记录。内容由当前 Agent 自带的看图能力理解；在你的项目中保存原件和结果，按需要应用清洗方案。

适合仪器说明、规格表和图文混排资料。默认保留原文，不翻译、摘要或删除重复内容。公式默认用 LaTeX；需要交给不支持数学渲染的系统时，可以明确要求使用带括号的等义文字表达。无法辨认的区域保留原图和疑点。

## 安装与准备

需要能查看图片、运行本地工具并写入项目的 Codex、Claude Code 或 WorkBuddy，以及 uv 0.8 以上版本。Agent 会按随包锁文件准备 Python 3.13 环境。无需配置额外模型、API Key 或 PDF 转换服务。

复制到当前 Agent：

```text
请从 https://github.com/cookaihq/cookai-skills 安装 pdf-to-markdown-vision 完整目录，保留已有设置，核对当前宿主能发现该 Skill，并检查运行环境。告诉我如何选中它。
```

1.0.0 已完成 Windows 本地开发与 Codex 验收；macOS 待验，具体宿主及范围见下文。

| 宿主 | 安装与调用 |
| --- | --- |
| Codex | 完整目录放入原生技能目录，或将 `~/.agents/skills/pdf-to-markdown-vision` 单项链接到本地检出；选中技能或使用 `$pdf-to-markdown-vision` |
| Claude Code | 完整目录放入 `~/.claude/skills/pdf-to-markdown-vision`，或单项链接到检出；使用 `/pdf-to-markdown-vision` 或在请求中点名 |
| WorkBuddy | 通过当前客户端的本地 Skill 管理入口导入完整目录，在技能列表选中后给出转换请求；复制安装须保留脚本、references、锁文件和 update.json |

Codex 的展示名为“PDF 视觉转 Markdown”，没有额外默认提示句。共享行为与内容规则只有一份。Windows 原生 Codex CLI 0.167.1 已在 workspace-write 默认沙箱中验证路径调用、真实样本、清洗、纠错与恢复；Claude Code、WorkBuddy 为兼容目标，未做业务实测；macOS、WSL 及 Codex GUI 交互待验。

## 第一次使用

转换会消耗宿主自身的额度；宿主无法提供准确用量时会说明无法测量。链接输入会下载原件；页面理解按当前宿主的数据处理方式进行。

在希望保存结果的项目中打开 Agent，选中 PDF 视觉转 Markdown，然后只发送一个 PDF 路径，例如：

```text
D:/资料/仪器说明书.pdf
```

也可只提供直接下载 PDF 的链接。文件可以在项目之外；只要会话已确定项目根，结果仍属于该项目。没有指定页范围就处理全文，没有默认清洗方案就保留原文。Agent 返回 Markdown、图片和任务说明的文件链接；用现有编辑器或宿主查看，不需要额外网页服务。

任务存放在项目的 `data/pdf-to-markdown/创建时间_文件短名_任务ID/`。其中 `source/` 保存原件，`results/v001/` 等保存可独立复制的结果，`README.md` 说明进度、问题与如何继续。若有失败页或待复核内容，会列明缺口；阶段结果不会替换已有完整结果。

## 可选清洗

清洗方案通过对话创建，不必手写配置。默认按项目保存，Skill 更新保留方案与任务资料。例如：

```text
为这个项目建立 knowledge 清洗方案：仅删除每页重复出现的公司品牌页眉，保留安全提示、脚注、单位和技术条件。把它设为项目默认。说明保存位置和实际生效来源。
```

长期方案位于 `config/pdf-to-markdown/cleaning/<方案名>.md`，说明用途、对象、匹配条件、保留例外和修改版本。项目默认路径保存在 `.env.local` 的 `PDF_TO_MARKDOWN_CLEANING_PROFILE`，保留无关配置。后续只给 PDF 路径就会采用有效默认。

本次覆盖可以这样说：

```text
转换这份 PDF 的物理第 7 页，本次不清洗，保留项目默认设置。
```

只对当前任务提出的要求不会改长期方案。采用清洗时仍保留 `raw.md`，另存 `cleaned.md`；`document.md` 是本版交付入口。选定方案丢失、不可读或意思不明确时，会报告问题并保留未清洗结果，不会静默跳过后声称清洗完成。

配置按每项首个非空值读取，同一文件重复字段取最后一次：

| 优先级 | 来源 |
| --- | --- |
| 1 | 当前进程环境变量 |
| 2 | 已选项目根的 `.env.pdf-to-markdown-vision` |
| 3 | 已选项目根的 `.env.local` |
| 4 | 已选项目根的 `.env` |
| 5 | 明确要求使用个人配置时，个人目录的 `.config/pdf-to-markdown-vision/.env` |

从项目子目录启动也使用已确定的项目根，不递归搜索父目录；相对方案路径也按该根解析。高优先级非空值会遮蔽低层设置；保存默认成功不等于覆盖已经生效。可以说“检查这个项目 PDF 转换的清洗配置，告诉我实际读取位置、来源，以及为什么新保存的默认没有生效”。

个人目录由实际运行 Python 的用户决定：

| 环境 | 个人配置位置 |
| --- | --- |
| macOS / Linux | 当前用户主目录下 `.config/pdf-to-markdown-vision/.env` |
| Windows 原生 | 当前 Windows 用户文件夹下 `.config\pdf-to-markdown-vision\.env`，例如 `C:\Users\你的用户名\.config\pdf-to-markdown-vision\.env` |
| WSL | WSL 内 Linux 用户主目录下的 `.config/pdf-to-markdown-vision/.env`；不自动读取 Windows 用户文件夹 |

这些是加载器路径约定，macOS、Linux 和 WSL 尚未实测。全局业务配置只有明确启用才参与；自动检查更新的开关独立读取，不需要启用业务配置。

## 继续、修订与排错

- “继续这个任务目录中的转换”：核对原件和有效进度，补上未完成页。
- “纠正这个结果的物理第 17 页保修表”：先根据记录解释当时做法，再保留历史、修订同一任务。
- “将这个任务换用 knowledge 方案重新清洗”：普通同版本重洗复用有效原始结果；不改其他任务。
- “回退这个任务到 v001”：只改变当前选择，其他版本保留。
- “解释这个输出中的公式对应哪一页、按什么规则处理”：读取记录和当时快照；没有记录的部分会明确说明无法核实。
- “这个图的标签有处理规则吗”：只咨询规则，不自动重转或修改规则。

程序会检查实际图片、相对引用和页文件，但语义仍需要 Agent 对照原页核验。不能可靠辨认时，查看对应疑点截图。尚未承诺通用跨页拼图、跨页拼表、手写或任意复杂扫描件识别。

同一任务只允许一个执行者写入；占用时先确认原会话是否还在工作。整个任务目录可以搬移复查，每个结果版本也可以单独复制阅读。磁盘不足时先清理其他空间，再让 Agent 继续任务。正常完成仅清理可再生缓存，失败与中断保留；Git 默认只追加运行数据忽略项，不取消已有文件跟踪。

## 更新

每次调用会自动检查更新，检查失败仍可继续当前任务。检查不是自动安装；真正更新需你确认。Git 安装通过当前检出更新，复制安装固定到已确认的 tag 和 commit，保留原版本以便失败恢复。

更新后再次处理旧任务使用新版规则并重做本轮目标页，任务 ID、原件、旧记录和结果仍在。安装更新不会自动重跑其他任务。

可以说“关闭 pdf-to-markdown-vision 的自动检查更新”。Agent 只修改个人 `.config/pdf-to-markdown-vision/.env` 的 `AUTO_UPDATE_CHECK=0`；该开关不读取项目配置。重新开启也通过对话完成。
