# git-setup

帮助你给新项目设置 Git，为已有项目添加远端仓库，并把主要远端已经发布的分支或标签同步到其他仓库。创建 Issue 时先读取项目约定：项目要求本地保存，就写本地文件并明确告诉你；项目使用 GitHub，就写到本次规则明确的仓库。

当前版本 **0.4.0** 支持仅提供仓库 URL 的默认接入流程，并增加仓库鉴权选择、持久凭证绑定、标准 Harness（项目内的 Git 操作脚本与配置）和明确调用 Skill 时的完整检查。本地 Issue 复用项目已有流程，文件仅在配置、执行或恢复确实需要时创建。三宿主完整验收仍未通过，具体结果见下方支持状态。需要 Node.js 20 或更新版本及 Git 2.29 或更新版本；Agent 会先检查环境。没有额外 npm 包、Python 环境或本地模型。

## 安装与第一次使用

把这段话复制给 Claude Code、Codex 或 WorkBuddy：

> 请安装 git-setup Skill，优先从 https://github.com/cookaihq/cookai-skills 安装，遇到网络故障时自动尝试 https://cnb.cool/zhidateam/tannt/tannt-skills ，仓库内目录是 git-setup。保留已有配置，核对当前客户端的 Skill 安装入口，并验证可以发现和调用它。

三宿主共用一份 Skill 源文件。Claude Code 的用户安装入口为 `~/.claude/skills/git-setup`，Codex 为 `~/.agents/skills/git-setup`；Git 检出可分别以每个 Skill 的符号链接挂载。WorkBuddy 桌面端按[腾讯官方安装器](https://github.com/Tencent/BrowserSkill/blob/main/crates/bsk-cli/src/skill_install/harness.rs)使用 `~/.workbuddy/skills/git-setup`，不假定支持符号链接；复制品由同一源版本更新，不独立维护。[CodeBuddy 官方文档](https://cnb.cool/codebuddy/codebuddy-code/-/git/raw/main/docs/skills.md)还提供项目目录 `.codebuddy/skills/git-setup`。本次 WorkBuddy 桌面实测加载的是项目副本，全局目录单独安装尚未验收；内嵌 CLI 与桌面的结果分别记录。

打开你的项目文件夹后，先说：

> 使用 git-setup，检查这个项目的 Git 状态、远端关系和 Issue 保存规则，先给检查结果。

只发送 Skill 名也会执行检查。预期会得到实际 Git 根目录、作者及来源、远端、分支跟踪、推送设置、鉴权来源和项目 Git 脚本的检查结果。缺项、未知项和需要选择的改动会分别说明，检查本身不改项目。Claude Code 可以显式使用 `/git-setup`，Codex 可以使用 `$git-setup`；WorkBuddy 在对话中点名 Skill。0.2.0 的项目副本加载及部分 URL 流程有历史验收证据；新增鉴权与 Harness 流程的客户端验收尚未完成，具体范围见下方支持状态。

## 常用请求

在 Agent 中打开要接入的项目后，可以只提供仓库地址，例如在 Codex 中输入：

> $git-setup https://cnb.cool/zhidateam/han/obvault_tannt

Claude Code 使用 `/git-setup <仓库地址>`；WorkBuddy 在对话中点名 git-setup 并附上地址。示例仅说明输入方式，不代表该 CNB 仓库已验证可访问或为空。

Agent 会读取当前项目状态和项目规则，查询远端，再按实际状态设置 Git。项目已有任何远端时，会列出全部远端，让你选择替换哪个地址，或以哪个新名称添加；相同地址也遵守这项选择。你已作出的明确选择会沿用。没有远端时使用 `origin`；这次自动采用的名称不算你已选择添加或替换，完成后再次只发 URL 仍会询问。

当前目录真正为空且远端有内容时，克隆直接落在这个目录。克隆后 Agent 会先读取取得的项目规则，再继续余下 Git 设置。当前目录已有文件而远端也有历史时，先与你明确文件保留及迁入方式。初始化缺少分支或作者时，只补问这些实际缺项。

尚无 Git 元数据的项目选择独立 GitHub Token 或 CNB 文件时，Agent 先建立 Git 元数据和忽略规则，再创建凭证空文件。你填写后，它才读取远端：远端有历史且目录只有本次准备文件时，取得并检出真实历史；另有文件时先明确保留及迁入方式。远端为空时补齐分支和作者设置。准备凭证本身不算项目接入完成，中断后会根据记录和实际文件继续检查。

默认终点是 Git 设置及远端读取验证。完成回复会明确写出 **“本次暂未提交和推送。”**，不会把接入成功说成代码已上传。普通 Git 接入不读取 Issue 规则。替换会影响分支、同仓其他 Worktree 及当前仓或管理仓的同步策略，Agent 会展示具体影响并沿用你的明确选择。

| 你可以这样说 | 会得到什么 |
| --- | --- |
| 只发送 git-setup 和一个仓库 URL | 为当前项目接入该远端；已有远端先选择替换或添加，完成后明确暂未提交和推送 |
| 从外仓入口选择已登记的 api 仓库，只发布它的 main | 列出 api 的实际检出、远端、引用和鉴权来源，按该仓策略执行并回读 |
| 给这个新项目设置 Git，初始分支用 main，作者用我确认的姓名和邮箱 | 初始化本地仓库并配置作者；首次提交的文件范围另按你的具体请求确定 |
| 保留现有 origin，增加这个 GitHub 仓库作为 github 远端 | 原远端保持现状，新远端地址得到回读核验 |
| 把 origin 已发布的 main 和 v1.0.0 标签同步到 backup | 先比较你指定的引用，再按授权同步并逐项核对 SHA |
| 这个项目的 Issue 存本地，继续使用原目录和编号规则 | Agent 读取已有本地规则，创建完成时明确返回“已保存到本地”和文件路径 |
| 这个子仓的 Issue 保存到外仓，另一个子仓保留自己的目标 | 分别明确每次操作的目标；仓库登记不会自动决定 Issue 继承 |
| 按当前项目规则创建一个 Issue，内容如下…… | 先解析本地/GitHub及归属，再写入唯一目标并回读 |
| 刚才创建结果不明，用原操作标识检查是否已创建 | 根据本地记录与实际目标核对，不重复创建 |

发布和同步会向远端传输指定历史。发布和同步都检查来源历史中的已知秘密模式和大文件，检查发现或预算不足时会停止；这不能保证识别所有秘密。同步只包含明确分支/标签；Git LFS 和子模块实际内容的传输尚未实现，检测到时明确报告内容未完成。目标分叉、同名不同对象标签、保护分支不会被强推覆盖。

首版通过标准 Git 传输接入已有 GitHub、CNB 等远端；GitHub.com 支持创建仓库及 Issue。其他在线 Issue 平台、GitHub Enterprise、CNB 仓库创建 API、双向自动合并及网页合并自动触发同步不在首版范围。创建远端仓库需要你明确所有者、名称、可见性及创建意图。没有新建远端的授权时，只设置已有目标。

## 项目配置与个人配置

远端地址保存在 Git 配置中，普通接入不再为复制地址创建 `.git-setup/`。你选择采用标准 Harness 后，Agent 会按项目规则提出安装位置，展示生成文件及规则修改；确认采用后，项目取得操作脚本、非敏感同步配置和说明，并在实际规则文件登记入口。入口可从其他工作目录调用，也可在移除 Skill 后继续使用。项目入口与 Git 凭证程序分别只携带所需运行文件；标准安装使用一份可恢复计划，不另外保存参数副本，完成后计划压缩为结果摘要。日常操作只核对必要运行文件、目标、来源和计划，不因无关 Issue 文档缺失而重新要求采用标准。同步只使用该项目脚本的配置，缺少时停止，不读取旧 JSON 同步设置。独立仓由实际 Harness 的 `repos.conf` 登记，子模块联合核对 Git 登记及元数据；旧 Issue 配置和 routing 已退出读写，使用者已有文件原样保留，不自动迁移。凭证保留在本机；生成文件不自动提交、推送、同步或创建 Issue。

每次使用 git-setup，Agent 都先检查项目已有 Git 脚本及其 hooks、CI 调用关系，再与标准行为比较。它会说明独有功能及替换影响，让你分别决定是否采用标准、哪些功能要重新实现。已有明确选择且事实未变时会继续沿用。选择保留现有工具时，只保存 Git 本机选择，不生成项目脚本或安装记录。可以说：“使用 git-setup，先比较这个项目已有的 Git 脚本与标准，再让我选择采用方式及要保留的功能。”

一份外仓项目脚本可以明确选择已登记的仓库及其 Worktree。各仓保留自己的远端名、分支、同步策略和账号；计划区分脚本安装位置、实际检出和凭证主检出。目标或来源变化会拒绝旧计划，未选仓不发生写入。未初始化的其他子模块不会阻断已选仓的操作；选中的仓库尚未初始化时会明确停止。升级会保留这些仓库已有的策略，不替你批量初始化。

标准发布和同步分别请求，不自动互相触发，也不自动新增标签、Release、hooks 或 CI。项目扩展按你的具体选择接入，可选“发布或同步成功后自动执行”或“只登记，明确调用才执行”；运行失败或中断后先检查记录和实际结果，不自动再次执行。

项目扩展由项目维护，建议放在所选脚本目录的 `extensions/` 中；已有目录外扩展仍可继续使用。升级会列出生成、保留和明确修改的文件，保留项目配置、独立仓登记、扩展及资源的内容和普通文件权限。没有重新选择的策略继续沿用；明确停用扩展只取消调用，保留文件。你可以说：“升级本项目的标准 Git 脚本，保留已有配置和扩展，先展示文件计划。” 对现有项目命令，可以说：“保留这个项目入口，只在我明确请求时调用；请登记入口并验证内容，不随普通发布或同步自动执行。”

远端身份不会随普通升级自动接受新地址。需要更换时，可以说：“核对新的远端目标和鉴权，在这次升级计划中明确刷新根仓目标身份。”升级中断后让 Agent 读取原记录，核对现存文件、阶段目录和备份；发现后续修改会停止，保留现场。

建议在首次使用前完成项目的 matt-pocock-skills 初始化；已初始化项目直接复用，禁止重跑的项目修复原文档或映射。Git 接入本身不强制安装它。仓库登记决定可管理的仓库范围，不自动决定 Issue 归属。Agent 读取现有 Issue tracker 文档及其引用，按项目的 Worktree 文档映射访问同一实体，再准备这一次操作的明确目标。规则或模板变化时重新读取；真正缺少规则时给初始化指引，项目禁止重新初始化时只提示修复现有文档或映射。可以直接按现有文字约定准备事项，不要求项目额外创建模板文件。普通 Git 设置不受无关 Issue 文档影响。

第一次设置 GitHub HTTPS 仓库时，Agent 会在对话里让你选择“使用本机 gh 已登录账号”或“使用这个仓库的独立 GitHub Token”，Token 选项同时写明准确保存路径。已有有效选择可以继续使用；公开仓库可以读取，也不能跳过这一步。gh 有多个账号时会让你选定一个，不会替你切换活动账号。

选择独立文件后，Agent 创建一个受保护空文件，并在同一条回复中给出可点击完整路径、填写格式、目标仓库、本次需要的权限和用途。你在本机填写后回复“已填写”，Agent 才继续验证。GitHub 文件写单行 Token 原文，不加引号或变量名。CNB 文件写单行完整鉴权 URL，格式为 `https://cnb:<访问令牌>@cnb.cool/<完整仓库路径>`。

文件按仓库分别保存：

- 单仓使用主检出根的 `.credentials/repositories/`；同仓 Worktree 读取同一实体。
- 外仓和已登记子仓集中使用明确统筹外仓的主检出根 `.credentials/repositories/`；目录嵌套本身不建立关系，各仓的账号选择仍独立。
- GitHub 文件名为 `<owner>--<repo>.github-token`；CNB 取完整仓库路径、各级用 `--` 连接并加 `.cnb-url`，例如 `zhidateam--han--obvault_tannt.cnb-url`。GitHub 与 CNB 分别保存。

新文件不会进入 Git；已有文件保留，路径冲突或失效时会说明具体来源。macOS/Linux 新目录权限为 700、文件为 600。gh 使用已保存的选定账号，Token 不复制到项目。设置还会把完整凭证读取程序安装到本仓实际 Git 元数据目录，Worktree 共用；即使移除 Skill，后续普通 Git 操作仍使用同一来源。旧版本凭证程序不会在普通 Git 操作中自动清理。需要时可以说：“检查这个仓库未使用的旧 Git 凭证运行包，按计划清理能确认安全删除的版本。”Agent 会保留仍被 Worktree 引用、正在运行、内容已修改或无法核验的包，不清理结果不明的业务记录。新 clone 需重新建立本机绑定；凭证轮换后让 Agent 重新验证原文件，失败时不切换其他账号。

可以这样说：

> 请用 git-setup 给这个仓库设置鉴权，在对话里让我选择本机 gh 账号或独立 Token。选择文件后请创建空文件，并把准确路径、格式和这次所需权限一起告诉我；我回复“已填写”后再验证。

代码读取使用相应读取权限，推送需要写权限，Issue 创建需要 Issue 写权限；Agent 按本次任务给出具体清单。CNB 只支持 HTTPS，部署令牌只能用于读取。当前默认设置验证身份和读取，不执行推送预检或实际推送。

已有环境配置继续兼容，且不会自动迁移到新文件。已有显式凭证配置的读取顺序为：进程环境 → 选定配置项目的 `.env.git-setup` → `.env.local` → `.env` → 显式启用后的个人 `.config/git-setup/.env`。不扫描父目录；凭证与主机、仓库必须同层成组提供。已经绑定独立文件或 gh 账号的目标始终使用该来源，不被另一份环境 Token 静默替换。新 Token 准备流程使用上面的独立文件位置。

Windows 原生使用其实际主检出的 `.credentials\repositories\`；WSL 使用 WSL 检出的 `.credentials/repositories/`，不自动读取另一环境的凭证。Windows ACL、原生 Git helper 与 WSL 新鉴权流程尚未实机验证。旧个人配置的路径如下：

| 环境 | 个人业务配置位置 |
| --- | --- |
| macOS / Linux | 当前 Node 运行用户个人文件夹下 `.config/git-setup/.env` |
| Windows 原生 | 当前 Node 运行用户文件夹下 `.config\git-setup\.env`，由 `os.homedir()` 定位，不改用 AppData |
| WSL | WSL 内运行用户的 Linux 个人文件夹下 `.config/git-setup/.env`；不会自动读取 Windows 的文件 |

这些路径说明来自实际加载器；操作系统和客户端的验证状态分别记录，不以路径存在证明兼容。

## 后续会话与恢复

Git 设置没有等待或恢复需要时不创建记录。需要跨轮确认时，Agent 会在已有工作区被忽略的 `data/git-setup/` 或 `tmp/git-setup/` 保存计划、已选目标与执行状态，告诉你实际位置；不把计划文件先放进待克隆的空目录。中断后让 Agent 读取原记录并重新检查实际 Git 状态，补齐未完成步骤。设置成功后同一记录自动压缩成结果摘要；未完成时保留完整恢复依据。记录保存不代表操作已经完成；克隆失败不会自动删除文件或直接重跑。远端替换会保留原远端跟踪引用，本次不刷新引用或证明两边历史关系。

后续 Issue 操作复用项目已初始化的 matt-pocock-skills 及现有规则。普通本地事项由 Agent 直接保存和回读 Markdown，不要求临时 JSON、操作编号或恢复文件。需要规格、拆票、实施时使用已有对应流程，不为普通建票再走一套工程流程。不另外生成 routing 文档、模板或长期默认值。已生成的 Git 项目入口按实际 Agent 规则登记；三客户端的新会话使用及恢复效果在完整实现后分别验证。

GitHub 写入，以及你明确选择使用脚本校验或恢复的本地操作，会把无凭证记录保存在目标项目的 `data/git-setup/`，该目录必须未被 Git 跟踪且实际被忽略。原始事项正文按你指定的本地目录保存，或发送到明确的 GitHub 仓库；操作记录保留目标、摘要和状态，便于跨会话核验。保存本地 Issue 不会提交或推送 Git。

这些脚本写入遇到中断后，让 Agent 使用原输入及操作记录核对。默认通过标准输入传递本次参数；只有跨会话确实需要且无法从已有任务完整重建输入时才保存原输入文件，并说明其位置与用途。创建和回复先按唯一标记查询、回读；更新检查原事项的实际内容。查询不到不能证明此前未写入，因此不会自动重发。原输入或规则变化、部分文件写入及后续用户编辑都会明确停止，保留实际内容。如果写入后最后一次规则或身份检查失败，Agent 会同时报告已写入的结果、原操作编号和复核问题，不重复创建。更新和回复使用原路径或链接；“参考这个 Issue 新建”按新建规则选择目标，并保留参考事项。

遇到问题，可以说：

- “检查 git-setup 实际读取哪个项目、哪些字段来自哪个文件，不显示凭证值。”
- “说明这次同步每个目标和引用的状态，只重试确认未完成的部分。”
- “检查这个子仓的管理关系，列出登记依据、实际检出和凭证来源。”

## 更新与支持状态

自动检查更新默认开启，检查失败仍可继续任务；实际替换版本需你确认。Git 检出随包提供 Bash 和 PowerShell 检查入口；复制安装用 `update.json` 确定稳定版本及 commit SHA，不假定宿主有未经核实的更新 API。可以说“关闭 git-setup 的自动检查更新”，它只修改个人 `.config/git-setup/.env` 的 `AUTO_UPDATE_CHECK=0`。这个开关独立于业务配置读取顺序。
